# ArchShell — Phase 1

## Why

A vision to realize, plus a pain to solve. Developers with low-to-medium architecture experience who hand features to an AI agent get code that drifts from any architecture, so they must review structure instead of business logic. ArchShell chooses the architecture once, records it as machine-readable rules, and enforces it with blocking gates on every agent change, so the developer delegates whole features and confirms only new business decisions. No current product closes the loop of pattern selection → recorded charter → generated tests → blocking gate on agent output, and .NET is underserved.

## Capabilities

Each capability's testable consequences live in the PRD companion under the cited FRs. Each capability is governed by the architecture spine's ADs.

- **CAP-1**
  - **intent:** The developer describes a new project, and ArchShell proposes the fitting pattern or combination from the catalog, asking discriminating questions when the request is unclear (FR-1–FR-8, FR-42).
  - **success:** On the golden set, at least 90% of selections are correct and there are 0 wrong automatic proposals; a proposal appears only when every FR-4 criterion holds, and otherwise the developer chooses between the top two.
- **CAP-2**
  - **intent:** ArchShell records the confirmed architecture as an ADR, `ARCHITECTURE.md`, and a machine-readable `architecture.yaml` that every feature reads first (FR-9–FR-11, FR-13).
  - **success:** After bootstrap, all three charter files exist and are consistent, and every feature workflow run reads the charter before generating anything.
- **CAP-3**
  - **intent:** ArchShell bootstraps the project atomically from the language pack's template: solution, projects, dependency wiring, feature backlog, and seeded vocabulary, with no business code (FR-15, FR-15a, FR-16, FR-17, FR-52).
  - **success:** A forbidden layer dependency does not compile. An interrupted or failed bootstrap leaves no partial project. A combination without a template ends in a gap report.
- **CAP-4**
  - **intent:** Every agent change passes per-edit checks and, at task completion or session stop, the full gates: build with warnings as errors, architecture tests, contract tests, and unit tests (FR-18–FR-22).
  - **success:** The gates detect 100% of the seeded-violation corpus for every shipped project template, and per-edit checks finish within NFR-1.
- **CAP-5**
  - **intent:** `archshell verify` re-runs every check in CI without a model and reports whether the platform can enforce owner approval (FR-41, FR-64).
  - **success:** `verify` fails on any protected change without a matching record, on generated files that differ from regeneration, and on any rule violation. On a platform without enforceable owner review, it reports *trust: unenforced* on every run.
- **CAP-6**
  - **intent:** ArchShell turns a feature request into a numbered spec, classifies each item into the closed intent set or a policy with three-run consensus, and draws every name from the domain vocabulary (FR-23, FR-43, FR-44, FR-58).
  - **success:** The intent golden set classifies 100% correctly under consensus. Any disagreement becomes a closed-choice question, and a new term always triggers an explicit synonym question.
- **CAP-7**
  - **intent:** ArchShell derives the feature plan from intents, tokens, and the pack's mapping table without a model, and asks for at most one confirmation, covering only new business decisions (FR-45, FR-54, FR-55, FR-59).
  - **success:** The same intents and tokens always produce the same plan. A fully derived feature proceeds with no confirmation. Plan extensions stay within their bounds.
- **CAP-8**
  - **intent:** Contracts are proposed as data in a closed type system, generated by the pack, confirmed in plain language when public, frozen before the RED test, and checked for breaking changes (FR-47–FR-51).
  - **success:** The same contract data produces byte-identical code. The agent cannot change a frozen contract. An unconfirmed breaking change fails the full gates and `verify`.
- **CAP-9**
  - **intent:** ArchShell scaffolds each feature's structure, composition, and policies from templates before implementation, and blocks any file, type, or member outside the confirmed plan (FR-24, FR-46, FR-56, FR-57, FR-60).
  - **success:** Scaffolding the same plan twice is byte-identical on every shipped project template. Out-of-plan files, types, or public members fail the gates. Authorization, audit, and transaction rules never appear in method bodies.
- **CAP-10**
  - **intent:** The agent implements each spec item test-first within bounded retries, and exhaustion or a misfit ends in a report instead of a relaxed rule (FR-25–FR-28).
  - **success:** For every shipped project template, a reference feature per intent (9 per template) runs end to end: spec, plan, contracts, scaffold, RED, full gates green. A task stops after 5 attempts with an exhaustion report.
- **CAP-11**
  - **intent:** When a feature needs a new module or contract location, ArchShell proposes charter growth within the immutable pattern and applies it only after developer confirmation (FR-29–FR-32).
  - **success:** Growth that would violate the pattern's rules is never proposed. Confirmed growth regenerates the charter, tests, and references consistently and adds a growth ADR.
- **CAP-12**
  - **intent:** The protected set changes only through confirmation flows that leave append-only records approved by human pull request review, and merge conflicts in generated files are resolved by regeneration (FR-14, FR-53, FR-61).
  - **success:** Every agent tampering attempt in the seeded-violation corpus is blocked in session or failed by `verify`. `reconcile` regenerates from both sides. An incompatible pair resolves to the decision already on the default branch.
- **CAP-13**
  - **intent:** Language packs, host adapters, providers, and CI providers plug into a core that does not change. A project pins the versions that generated it and upgrades only explicitly (FR-33–FR-38, FR-40, FR-62, FR-63).
  - **success:** A new extension is enabled only after passing the extension conformance suite. A newer ArchShell release never changes an existing project's generated files unless `archshell upgrade` runs. The runtime never reads `02-ARQUITECTURA`.
- **CAP-14**
  - **intent:** ArchShell converses in English or Spanish, following the developer, and generates every artifact in English (FR-12, FR-39).
  - **success:** A Spanish request receives Spanish questions and reports, and every generated file is in English.

## Constraints

- The architecture spine's AD-1–AD-23 bind every unit. Examples: the engine is a stateless state machine behind a closed action protocol, the engine owns every verdict, generated and seeded files are distinct classes, and Jinja2 is the single generator.
- Determinism (NFR-4): the same inputs produce the same scores, charter, tests, plans, scaffold, contracts, and verdicts, byte for byte on Windows, macOS, and Linux.
- `archshell verify` needs no model and no network beyond package restore (NFR-5). Project code goes only to the host's own model (NFR-6).
- Per-edit checks finish in at most 3 seconds (NFR-1).
- Every model output is schema-validated, with at most 2 retries, configurable (NFR-7).
- Toolchain: .NET 10 LTS or later, and Python 3.12 or later installed with `uv` or `pipx` (NFR-3).
- The chosen pattern and its rules are immutable. The charter only grows within the pattern, and a rule is never relaxed to pass a gate.
- Phase 1 launch: Claude Code host adapter, and a .NET/C# pack with all 21 project templates, each shipping the full feature workflow. The only Phase 2 command in the launch is `archshell verify`.
- The runtime is self-contained: it reads only shipped plugins plus the optional extra catalog path (FR-40).

## Non-goals

- Existing codebases (brownfield).
- Changing the chosen pattern after bootstrap.
- Functional correctness of business logic, and judging the quality of the agent's tests.
- Identical code across runs; only the process and the gates are deterministic.
- In Phase 1: the standalone CLI beyond `verify`, LLM providers other than the host's own agent, language packs other than .NET/C#, host adapters other than Claude Code, and CI providers other than GitHub.
- Adoption metrics.

## Success signal

- A developer bootstraps a new .NET project from a plain request. They then hand the agent a feature with no new business decisions, and it lands as a pull request with all gates green, without the developer confirming or reviewing structure. On the same template, every member of the seeded-violation corpus is blocked or failed by `verify`.
