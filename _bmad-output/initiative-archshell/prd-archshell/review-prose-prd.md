# ArchShell PRD - Editorial Prose Review

**Purpose read:** this document exists to help the product owner, architect, and implementers of ArchShell v1 agree on what the launch must do and why, and to trace every testable behavior to a stable FR ID.

**Style, tone, and voice to preserve:** terse, declarative, present tense ("ArchShell writes...", "The agent cannot..."). Bold principle statements and short, testable consequence bullets. Technical jargon is intentional (RED test, merge base, CODEOWNERS, NetArchTest). FR cross-references in parentheses are a deliberate traceability device. The journeys use italics for quoted dialog and a persona narrative. Keep all of these.

**Scope:** structure findings in `review-structure-prd.md` are already applied and not re-raised. Requirement meaning is not challenged. Every row is about expression: ambiguity, antecedents, overloaded sentences, term consistency, or style. Rows are ordered by how much each issue could cause two readers to implement different behavior.

**Minor cosmetic fixes (11):** section headings use title case ("Product Principles", "Key User Journeys", "Functional Requirements", "Non-Goals (Explicit)") while FR titles use sentence case; Microsoft style prefers sentence case throughout. FR-19 "check implementations conform" → "check that implementations conform". FR-5 "the question budget" → "the question limit (FR-3)". FR-28 "the exhausted failures" → "the failures that exhausted the retries". FR-22 "retry attempts" → "attempts" (matches FR-26). UJ-2 step 2 "a RED test is written against it first" → drop "first" or say "before any implementation". NFR-6 "sends project code to no service other than" → "sends project code only to". FR-8 bullet 3 "whether it will end in a gap report" → "whether that choice will end...". FR-58 bullet 4: the `status` example has no stated meaning; consider "(for example `people` → `person`; `status` unchanged)". FR-40 and §8: `02-ARQUITECTURA` appears without a gloss at first use in §8. FR-15a bullet 1 lists "the developer cancels" as a failure; consider "If scaffolding fails or is cancelled (for example...)".

## Summary

- **Total findings:** 26 table rows plus 11 grouped cosmetic fixes (37 in all).
- **High impact (could cause different implementations):** rows 1-5 (charter-growth scope, the conformance-gate name collision, whether the plan is confirmed, the FR-4 critical-driver criterion, and the scope of "task").
- **Pattern behind most rows:** terms that changed meaning as the FR-43–FR-60 patches landed ("contract" versus "contract location", "intent set", "internal", "template", "confirmed"). A few glossary additions (task, bootstrap, core, critical driver) and consistent use of qualified terms would resolve about half of the rows.
- No length target was given; the prose fixes are word-neutral.
