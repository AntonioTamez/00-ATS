# PRD Quality Review — ArchShell PRD (v2, after FR-43–FR-52)

Scope of this pass: the whole PRD and `addendum.md`, with priority on FR-43–FR-52 and the edits to FR-1, FR-15a, FR-24, FR-33, NFR-4, 4.5, 7.2, UJ-1, UJ-2 and the Glossary. Findings resolved since `review-rubric.md` (NFR section, seeded-violation corpus, metric targets, FR-14 mechanism via CI, retry accounting, FR-31 assumption, FR-17 solo path, ID order note, section numbering) are not repeated.

## Overall verdict
The new feature-plan and contract mechanism is the right move for the thesis: it extends "the model never decides structure" from bootstrap down to every feature, and the rejected alternatives in the addendum are argued honestly. What is at risk is the enforcement plumbing around it. The new artifacts (feature plans, generated contract code) are declared protected, but FR-14 still only admits changes from charter growth, so there is no defined, CI-verifiable way to authorize a plan extension, a contract revision or a breaking change. The two "closed sets" the whole mechanism rests on (intents, contract types) are given only by example and miss common cases (collections, optional values, new data types), and "the agent only fills bodies" has no answer for modifying existing files. Launch scope also grew substantially (mapping tables, building-block and contract templates, and contract comparison for 18 patterns plus 3 combinations) without 7.1, 7.2 or the metrics acknowledging it.

## Decision-readiness — adequate
The new mechanism is stated as decisions, not considerations: FR-43 "The model never selects building blocks, file paths, or names directly", FR-44 "never resolved by majority vote or by the model alone", and FR-47 "as data ... never as code". The addendum names what was given up (scaffold-all-then-delete; hand-written contracts; model-written contract code), which is exactly the trade-off disclosure the rubric asks for. The Assumptions Index records the one confirmation that mattered (FR-44 on by default).

What is not surfaced is the price of the new strictness. Three classification runs per spec item (FR-44) multiply model cost and add disagreement questions for every feature, and plan conformance (FR-46) will stop the agent whenever it needs a helper type or a wiring edit the mapping table does not know. Both push directly on the "Exhausted retries ... defeats the Delegate job" counter-metric, but neither cost is named, bounded, or measured.

### Findings
- **medium** Cost of consensus and plan strictness is unnamed (§ FR-44, FR-46, Success Metrics counter-metrics) — "Intent classification runs three times per spec item" triples classification calls and can add a question per disagreeing S#; FR-46 adds a stop-and-confirm for every out-of-plan type. The counter-metric "Unnecessary questions" is defined only for selection ("questions that did not change the selected pattern"). *Fix:* Add a counter-metric for feature-workflow interruptions (consensus questions + plan extensions per feature) and state the expected cost of FR-44 as a trade-off, or an NFR bound on model calls per spec item.

## Substance over theater — strong
The new FRs are mechanism, not furniture: each has a testable consequence, and UJ-2 now shows the plan and the plain-Spanish contract in use. The addendum's YAML snippets are clearly labelled illustrative. No new persona or differentiation padding was added.

### Findings
- **low** 4.5 overstates the model's narrow role (§ 4.5 Description) — "The model only classifies intents, proposes contract data, and fills method bodies" omits things the model still does: writes the spec S1..Sn and gap questions (FR-23), supplies verb/noun tokens (FR-43), writes the RED test body (FR-25), and extracts capabilities (FR-1). *Fix:* List them, or reword to "The model never decides structure or contract code; it ...".

## Strategic coherence — adequate
The new FRs follow from the thesis: the plan conformance gate (FR-46) and contract freeze (FR-50) close the last place where the agent could invent structure. The feature backlog (FR-52) connects bootstrap to the Delegate job cleanly, and keeping bootstrap free of business code (FR-15a) is a good scoping decision.

The coherence problem is scope. The prior review flagged "18 templates vs depth thesis" as medium. FR-33 now multiplies that surface: for each supported pattern a pack must ship building-block templates, a complete intent mapping table, contract templates, and public-contract comparison, and FR-33's consequence applies it to "every shipped project template (FR-15)", i.e. 18 patterns plus 3 combinations. 7.1 still describes the launch pack as "templates for all 18 catalog patterns plus three combinations (FR-15)", which now understates the commitment by roughly 4x. Metrics do not measure the new layer at all: the seeded-violation corpus is defined over rule types from `architecture.yaml`, not over plan non-conformance or unconfirmed breaking changes.

### Findings
- **high** Launch scope silently multiplied by FR-33 (§ FR-33, 7.1, addendum Competitor risk) — Each of 21 shipped templates now needs building-block templates, a full mapping table, contract templates and a comparison, and it is ambiguous whether mapping tables are per pattern ("for each supported pattern") or per template (the addendum's table is for the combination "Clean + Screaming"). *Fix:* State in 7.1 what the pack ships per template; resolve per-pattern vs per-template; and either justify the full breadth or restrict feature-workflow support at launch to a named subset with the rest ending in a gap report (FR-17).
- **medium** Metrics and acceptance do not cover the new gates (§ 7.2, Success Metrics Primary, FR-37) — 7.2 adds only byte-identical scaffolding. Nothing verifies that FR-46 rejects out-of-plan types, that FR-51 catches an unconfirmed breaking change, that every mapping table is complete (FR-33), or that consensus disagreement becomes a question (FR-44). FR-37's conformance suite ("golden set + engine contract tests") would admit a community pack with no mapping tables. *Fix:* Extend the seeded-violation corpus with plan-conformance and breaking-change cases; add FR-33 completeness to 7.2 and to the FR-37 conformance suite.

## Done-ness clarity — thin
Most new FRs have crisp consequences ("byte-identical", "never by majority vote", "same intents and tokens always produce the same feature plan"). But three boundaries the engineer needs on day one are undefined, and each sits on the critical path of every feature.

First, the closed sets. The Glossary defines Intent as "a closed set (for example state change, query, side effect, new concept, external integration, validation rule)". A closed set given "for example" is not closed, and FR-33's test "every intent in the closed set maps to at least one building block" cannot be run until the set is enumerated; the addendum's table maps only three intents. FR-47's type set ("primitives, entity identifiers, money, enums, and contracts or data types that already exist") has no collections (a `query` intent cannot return a list of appointments), no optionality (the addendum itself uses `string?` and `money?`), and no way to introduce a new data type or enum, which almost every new feature needs. "A proposal that duplicates an existing type instead of reusing it is rejected" has no deterministic definition of "duplicates" (name? shape?).

Second, the modification path. FR-45 says an existing building block "becomes a modification instead of a new file" (UJ-2: "the existing `Appointment` entity is marked as modified"). FR-24 says scaffolded files hold fixed signatures and "the agent only fills bodies", and FR-46 blocks creating types not in the plan. No FR says who adds the new members and signatures to a modified file (a `Cancel` method, a `Status` field), what edits inside it are allowed, or how the full gates decide that a modified file "matches its plan". Composition-root wiring (DI registration), persistence mapping and migrations are not building blocks in the addendum's table, so either the agent is blocked on every feature or those files are a loophole.

Third, consensus agreement. FR-43 allows "one or more intents" per item, but FR-44 only says "Agreement is accepted". Whether agreement means identical intent sets, and whether the verb/noun tokens must also agree (they determine every name, FR-45), is unstated, so plan determinism across runs is not guaranteed by consensus.

### Findings
- **high** Closed intent and type sets are not closed (§ Glossary "Intent", FR-43, FR-47, FR-33, addendum mapping table) — Intents are listed "for example"; the type set lacks collections, optional values and new data types/enums; "duplicates an existing type" is undefined. *Fix:* Enumerate the intent set in the PRD as core-owned and versioned (FR-36), since adding an intent breaks every pack's FR-33 completeness; extend the type set with list/optional and "new data type defined in this plan"; define duplication deterministically (for example same name, or same field set).
- **high** Modification and wiring path undefined (§ FR-45, FR-24, FR-46, UJ-2 step 1) — "becomes a modification", "the agent only fills bodies" and "blocks ... creating files or types that are not in the confirmed feature plan" cannot all hold when a feature adds members to an existing entity or registers an adapter. *Fix:* Add a consequence defining what a modification permits (template-generated member stubs vs agent-added members), list the wiring files the agent may edit outside the plan (or make them building blocks), and define "files match the plan" for FR-46's full-gate check, including private/nested helper types and extra test files.
- **medium** Consensus agreement undefined (§ FR-44, FR-43) — It is unclear whether agreement compares intent sets, tokens, or both. *Fix:* "Agreement means all three runs return the same intent set and the same verb/noun tokens for the item; any difference in either is a disagreement."
- **medium** Schema validation and retry bounds rest on an out-of-scope FR (§ FR-43, FR-47, FR-35, 7.1) — FR-43 cites "schema validation (FR-35 rule)", but FR-35 is excluded from launch in 7.1, and "retried within bounds" (FR-43, FR-47) joins FR-1's still-unbounded "a bounded number of times". *Fix:* Move "every model output is validated against a core-owned schema; N retries, then error" into a core FR that is in scope, and give N (or name it configuration with a default).
- **medium** Breaking-change baseline and definition (§ FR-51) — "compares it with the previous version" does not say previous to what (last commit, default branch, last confirmed plan), and "for example a removed operation or a changed type" leaves added required inputs, renamed fields and nullability changes open. *Fix:* Name the baseline (for example the contract on the default branch) and either list breaking-change classes or state that each language pack defines them in its FR-33 comparison with a minimum set.
- **low** Preview before generation (§ FR-49 vs FR-48) — "The developer can ask to see the generated code before confirming", but FR-48 generates code "from the confirmed contract data". *Fix:* State that a preview is generated from the unconfirmed data and discarded if not confirmed.
- **low** Revision after freeze (§ FR-50) — When a frozen contract is revised, it is unspecified whether the RED test, generated contract code and already-written implementation are regenerated, and whether this resets the FR-26 attempt count. *Fix:* One consequence covering both.
- **low** "Nothing ... is silently dropped" has no oracle (§ FR-52) — Capabilities are model-extracted (FR-1), so there is nothing to test "silently dropped" against. *Fix:* Reword to the observable behavior: "every extracted capability is shown in the backlog for confirmation before it is written."

## Scope honesty — adequate
Out-of-scope lists are explicit and the Assumptions Index is honest ("None open"). The addendum's "Relationship with charter growth" paragraph is a genuinely useful scope boundary, but it lives in the wrong document.

The structural gap is the authorization path for the new protected artifacts. FR-46 says confirmed plans "belong to the protected set (FR-14)", and FR-48 says generated contract code does too. FR-14's protected-set list does not include either, and FR-14 blocks every change "that do[es] not come from the charter growth flow (4.6)". Plan extensions (FR-46), contract revisions (FR-50) and breaking-change confirmations (FR-51) are not charter growth, so as written they are tampering. FR-41 checks a growth record only for `architecture.yaml` changes; there is no equivalent record that lets `archshell verify` tell a developer-confirmed plan change from an agent edit, and no CODEOWNERS/PR rule (FR-30) for plans or public contracts.

### Findings
- **high** No authorized path for changing protected feature artifacts (§ FR-14, FR-46, FR-48, FR-50, FR-51, FR-41) — FR-14's enumerated protected set omits feature plans and generated contract code, and admits changes only through charter growth; plan extension, contract revision and breaking-change confirmation have no recognizable, CI-checkable record. *Fix:* Add plans and generated contract code to FR-14's list; define a "feature confirmation" flow alongside charter growth that FR-14 accepts; make FR-41 fail on a plan or contract-code change without a matching confirmation record; decide whether public-contract changes need CODEOWNERS review like the charter.
- **medium** Charter growth vs feature-level contracts boundary only in addendum (§ FR-29, FR-31, Glossary "Charter growth", addendum Contract Mechanism) — FR-29 and the Glossary say growth covers "a new module or contract"; FR-47 lets a feature propose new public contracts. Only the addendum says "declaring a new contract location ... is charter growth; adding or changing operations inside declared contracts is feature-level". *Fix:* Move that sentence into FR-29 or the Glossary entry for Charter growth.

## Downstream usability — adequate
The Glossary gained four precise entries (Intent, Building block, Feature plan, Contract) that story creation will lean on. Two problems: "contract" now names three different things, and the flagship journey contradicts the workflow order.

UJ-2 step 1 confirms the plan (including "a notification port"), freezes the contract and writes the RED test; step 2 then discovers that a `Notifications` module is missing and grows the charter. But FR-45 derives building-block paths from the charter's modules, so the plan confirmed in step 1 could not have placed the notification adapter, and the 4.5 sequence ("read charter → spec → ... → gates") has no step for charter growth or plan extension at all.

### Findings
- **medium** UJ-2 order contradicts 4.5 and FR-45 (§ UJ-2 steps 1–2, 4.5 Description, FR-45, FR-29) — Growth occurs after the plan is confirmed and frozen, yet the plan depends on the modules growth adds. *Fix:* Put "propose charter growth if needed" between spec and plan derivation in the 4.5 sequence, and reorder UJ-2 so growth precedes the plan (or show it as a FR-46 plan extension after growth).
- **medium** "Contract" is overloaded (§ Glossary "Contract", FR-19, FR-36, FR-37) — The Glossary defines a feature-level contract; FR-36 "Versioned contracts" and 7.1 "versioned extension contracts" mean plugin interfaces; FR-37 "engine contract tests" means the engine JSON interface; FR-19 contract tests mean OpenAPI/JSON Schema conformance. *Fix:* Rename FR-36/FR-37 uses to "extension contract" / "engine interface tests" and add them to the Glossary.
- **low** Glossary entry is pattern-specific (§ Glossary "Contract") — "Internal contracts are ports owned by the Application layer" does not hold for patterns without an Application layer (for example Vertical Slice, Transaction Script). *Fix:* "owned by the module's inner layer, as the pattern defines it."
- **low** Missing terms (§ Glossary) — New: mapping table, plan extension, frozen contract, breaking change, feature backlog, verb/noun tokens. Carried over: golden set, conformance suite, gap report, exhaustion report, critical driver. *Fix:* Add them.

## Shape fit — strong
Capability-spec shape with two load-bearing UJs still fits a single-operator developer tool. The technical "how" of the new mechanism is correctly kept in the addendum as illustrative, leaving the PRD at the requirement level. UJ-2 now shows the plain-language contract, which is the user-facing proof that FR-49 serves a junior developer.
