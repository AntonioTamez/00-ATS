Arquitectura Onion
para novatos

Una arquitectura en capas “dada la vuelta”: el modelo de dominio va en el centro y todo lo demás, incluida la base de datos, queda afuera. Aquí aprenderás qué resuelve, qué va en cada anillo y cómo replicarla.

1. ¿Qué problema resuelve?

Jeffrey Palermo (2008) criticó las capas tradicionales: cada una depende de la de abajo, así que la lógica de negocio termina acoplada al acceso a datos. En sus palabras, “las dependencias transitivas siguen siendo dependencias”. Compara:

Los 3 principios (de Palermo)

  • Las capas internas definen interfaces; las externas las implementan.
  • El acoplamiento apunta hacia el centro.
  • El núcleo compila y se ejecuta sin la infraestructura.

Y una diferencia clave: una capa puede usar directamente cualquier capa más interna (no solo la contigua). Lo que nunca puede es depender de una más externa.

Nota honesta: Palermo advierte que no es para sitios web pequeños; encaja en aplicaciones empresariales longevas con comportamiento complejo.

↑ todas las dependencias apuntan al centro ↑

Matiz: en sus artículos, Palermo habla de un núcleo con infraestructura, UI y tests afuera, y dice que el número de capas varía. Los cuatro anillos son la forma en que lo enseñan fuentes secundarias; es una convención útil, no un mandato del autor.

¿Dónde pongo esta regla?

  1. ¿Afecta a una sola entidad? → dentro de la entidad (Order.Place).
  2. ¿Involucra varias entidades? → servicio de dominio (OrderPlacementService).
  3. ¿Es orquestar pasos (cargar, llamar al dominio, guardar)? → servicio de aplicación.
  4. ¿Es un detalle técnico (SQL, HTTP, reloj)? → anillo exterior.

3. Recorrido de una petición

Ejemplo: POST /api/orders con 2 unidades a 60 € para un cliente.

4. Estructura de la solución

Shop/
├─ src/
│  ├─ Shop.Domain.Model/       ← anillo 1: Order, Customer, Money, DomainException
│  ├─ Shop.Domain.Services/    ← anillo 2: IOrderRepository, ICustomerRepository, OrderPlacementService
│  ├─ Shop.Application/        ← anillo 3: PlaceOrderService, CancelOrderService, DTOs, IClock
│  ├─ Shop.Infrastructure/     ← anillo 4: repositorios, SystemClock
│  └─ Shop.Api/                ← anillo 4: endpoints + composition root
└─ tests/Shop.Tests/           modelo · servicios de dominio · aplicación · arquitectura · API

Un detalle que sorprende: la infraestructura referencia varios anillos

Es correcto y es la regla de Palermo: una capa externa puede usar cualquier capa interna. Shop.Infrastructure implementa interfaces del anillo 2 (IOrderRepository) y del anillo 3 (IClock), y reconstruye entidades del anillo 1.

// anillo 2 define lo que necesita
public interface IOrderRepository { Task<Order?> GetByIdAsync(Guid id, CancellationToken ct); ... }

// anillo exterior lo implementa
internal sealed class InMemoryOrderRepository : IOrderRepository { ... }

Verificación en el binario

Los ensamblados compilados se inspeccionaron con REA (análisis estático de metadatos):

  • Shop.Domain.Model.dll → ninguna referencia Shop.*
  • Shop.Domain.Services.dll → solo Shop.Domain.Model
  • Shop.Application.dll → Shop.Domain.Model y Shop.Domain.Services
  • Shop.Infrastructure.dll → los tres anillos internos, no Shop.Api

Anillos de Onion dentro del núcleo + casos de uso como eje (Clean) + rigor de puertos y adaptadores en la frontera (Hexagonal) + tests de arquitectura. Detalle en docs/ONION-VS-CLEAN-VS-HEXAGONAL.md.
