Event Sourcing
para novatos

En vez de guardar "hay 7 en stock", guardas lo que pasó: "llegaron 10", "salieron 3". El 7 se calcula repitiendo los hechos. Nada se edita ni se borra: lo que se equivoca se corrige con otro hecho.

1. La idea

CRUD

Una fila con el valor actual. Cambiar es sobrescribir: el pasado se pierde, salvo que añadas una auditoría aparte.

Event Sourcing

Una lista de hechos que solo crece. El estado actual es lo que sale de repetirlos. El historial es el dato.

El precio

Más piezas: versionar eventos, controlar la concurrencia, construir lecturas aparte, cuidar los datos personales.

2. Libro mayor: añade hechos y repítelos

Ejecuta comandos. Cada uno decide (puede rechazarse) y, si procede, añade un evento. El número grande no se guarda: se reconstruye.

3. Snapshots: una caché, no la verdad

Con miles de eventos, repetirlos todos en cada carga es lento. Cada N eventos se guarda una foto del estado; cargar = foto + los eventos posteriores.

Los tests prueban que cargar con o sin snapshot da exactamente el mismo estado, y que se puede borrar el snapshot y reconstruirlo.

4. Dos empleados a la vez: concurrencia optimista

Los dos cargan el artículo en la misma versión y deciden con lo que ven. El almacén solo acepta el primero que escriba: el otro debe recargar y volver a decidir.

5. Los eventos viejos no se reescriben

Un día cambia la forma de un evento. Los ya guardados no se tocan: un upcaster los convierte al leerlos.

8. Errores típicos

Eventos sin intención

StockChanged(42) pierde el porqué. Prefiere StockShipped(4, "ORD-1").

Editar o borrar un evento

Rompe la historia. Se corrige con un evento compensatorio.

Validar al reproducir

Una regla nueva impediría reconstruir el pasado. Apply no valida.

Cambiar un evento sin upcaster

Los viejos dejan de poder leerse.

Datos personales en los eventos

Chocan con el derecho al olvido. Guárdalos fuera o cífralos por sujeto.
