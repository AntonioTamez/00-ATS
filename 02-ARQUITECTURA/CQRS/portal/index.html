CQRS
para novatos

Separar lo que cambia datos de lo que los lee. Dos modelos, cada uno hecho para su trabajo, unidos por eventos. Con un precio: la lectura puede ir un paso por detrás.

1. La idea

Command

Una intención de negocio: "depositar 50". Cambia el estado, pasa por las reglas y devuelve casi nada (un id).

Query

Una pregunta: "dame el resumen de la cuenta". Devuelve datos ya preparados para la pantalla y nunca cambia nada.

Eventos y projector

Cada cambio deja un evento en un log. Un projector los lee y actualiza el modelo de lectura. Entre un paso y otro, la lectura está desactualizada.

3. Tres niveles de CQRS

Elige un nivel.

El ejemplo de este kit es el nivel 2, en memoria. No es Event Sourcing: el estado de Account se guarda tal cual y el log solo alimenta la lectura.

Cómo se ve en código

// COMMAND: intención de negocio, devuelve un id o nada

Se combina con DDD (modelo de escritura), con Clean/Hexagonal (organización) y con Vertical Slice (cada comando o consulta en su carpeta). No es lo mismo que Event Sourcing ni que Event-Driven.

6. Errores típicos

Comandos que devuelven datos

Devuelve un id; que el cliente consulte. Si no, mezclas lectura y escritura otra vez.

Ignorar la consistencia eventual

El usuario hace algo y no lo ve. Diseña la pantalla para ello.

Reglas en los handlers

El handler orquesta; la regla vive en el dominio (Account.Withdraw).

Projector sin idempotencia

Un reintento duplica datos. Guarda el último evento aplicado.

CQRS en un CRUD

El doble de código para nada. Empieza simple.

"CQRS = Event Sourcing"

Son cosas distintas; no necesitas un broker ni eventos como fuente de verdad.
