Vertical Slice
para novatos

En vez de organizar el código por capas técnicas (controllers, servicios, repositorios), lo organizas por funcionalidad. Cada funcionalidad es una “rebanada” que contiene todo lo que necesita, del HTTP a la base de datos.

1. ¿Qué problema resuelve?

Un cambio real casi siempre es una funcionalidad (“permitir cerrar un ticket”). En una arquitectura por capas, eso toca una pieza en cada capa. Elige qué cambio quieres hacer y mira qué se modifica:

La idea de Bogard

“Minimize coupling between slices, and maximize coupling in a slice.”
  • Entre slices: casi nada. Una slice no llama a otra.
  • Dentro de una slice: todo junto: request, lógica, respuesta, endpoint.
  • Una funcionalidad nueva solo añade código: no modificas código compartido ni temes efectos colaterales.

2. Anatomía de una slice (haz clic)

Cada slice elige su enfoque

SliceTipoEnfoque
OpenTicket, AssignTicket, CloseTicketComando (escribe)Carga la entidad Ticket, llama a su método, guarda
GetTicketQuery (lee)Proyección directa a un DTO, sin entidad
ListTicketsQuery (lee)Filtro + paginación + validación propia

Sin repositorios obligatorios: el handler usa el AppDbContext directamente. Sin mediator obligatorio: el endpoint llama al handler.

Ejemplo: POST /api/tickets/{id}/close con una resolución.

4. Estructura de la solución

Helpdesk/
├─ src/Helpdesk.Api/
│  ├─ Common/                    ← poco y justificado
│  │  ├─ Ticket.cs               reglas de negocio compartidas
│  │  ├─ AppDbContext.cs
│  │  ├─ Errors.cs               errores → HTTP (422, 400, 404)
│  │  └─ FeatureRegistration.cs  único sitio que lista las slices
│  └─ Features/
│     ├─ OpenTicket/    OpenTicket.cs     (Request · Response · Handler · Endpoint)
│     ├─ AssignTicket/  AssignTicket.cs
│     ├─ CloseTicket/   CloseTicket.cs
│     ├─ GetTicket/     GetTicket.cs
│     └─ ListTickets/   ListTickets.cs
└─ tests/Helpdesk.Tests/         entidad · cada slice · API · aislamiento

¿Qué va en Common?

  • Sí: las reglas de negocio de un concepto que varias slices modifican (Ticket), el DbContext, el traductor de errores.
  • No: formas de respuesta, validaciones de una petición, consultas: se quedan dentro de su slice, aunque se parezcan a otra.

Una pequeña duplicación entre slices suele costar menos que acoplarlas. Lo que no debe copiarse son las reglas de negocio.

Cómo se impone la frontera

Hay un solo proyecto, así que el compilador no impide que una slice use a otra. Por eso existe un test de aislamiento que falla si una slice nombra a otra. Además, los binarios compilados se verificaron con REA (análisis estático de llamadas IL):

  • 937 llamadas analizadas: 195 dentro de una misma slice, 27 hacia Common.
  • 0 llamadas entre slices y 0 de Common hacia una slice (salvo el registro).

5. Vertical Slice vs Clean / Hexagonal / Onion

No es “lo contrario”: son ejes distintos. Las otras responden cómo protejo el negocio de la tecnología; Vertical Slice responde cómo organizo el código para que los cambios sean locales.

Cuándo combinarlas

Slices como estructura principal + un dominio compartido rico donde haga falta (como Ticket) + puertos y adaptadores solo dentro de las slices que integran algo externo. Detalle en docs/VERTICAL-SLICE-VS-CAPAS.md.
