Clean Architecture
para novatos

Una forma de organizar tu código para que las reglas de tu negocio no dependan de la base de datos, el framework web ni ninguna librería. Esta página te explica la idea, qué va en cada capa y cómo replicarla.

1. ¿Qué problema resuelve?

Sin arquitectura

Un controller que valida, calcula, hace SQL y devuelve JSON. Para probar una regla necesitas servidor + base de datos. Cambiar de base de datos significa tocar todo.

Con Clean Architecture

Las reglas viven en el centro, sin conocer nada de afuera. La base de datos y la web son detalles enchufables. Pruebas rápidas, cambios localizados.

La Regla de Dependencia (la única que debes memorizar)

El código de una capa solo puede conocer capas más internas. Nunca al revés.

“Nada en un círculo interno puede saber nada sobre algo de un círculo externo.” — Robert C. Martin, 2012

¿Dónde pongo este código? (3 preguntas)

  1. ¿Es una regla que existiría aunque no hubiera software? → Domain
  2. ¿Es “lo que hace la aplicación” (orquestar pasos)? → Application
  3. ¿Es un detalle técnico (SQL, HTTP, archivos, email)? → Infrastructure / API

El truco: puertos y adaptadores

El caso de uso necesita guardar datos, pero no puede depender de la base de datos. Por eso Application define una interfaz (puerto) y Infrastructure la implementa (adaptador). El control va hacia afuera, pero la dependencia de código apunta hacia adentro.

// Application  (define QUÉ necesita)
public interface ITodoRepository { Task AddAsync(TodoItem item, CancellationToken ct); }

// Infrastructure  (decide CÓMO se hace)
internal sealed class InMemoryTodoRepository : ITodoRepository { ... }

// Api/Program.cs  (los conecta)
services.AddSingleton<ITodoRepository, InMemoryTodoRepository>();

4. Estructura de carpetas

TodoApp/
├─ src/
│  ├─ TodoApp.Domain/            ← reglas del negocio
│  │  ├─ DomainException.cs
│  │  └─ Todos/TodoItem.cs
│  ├─ TodoApp.Application/       ← casos de uso + puertos
│  │  ├─ Abstractions/ITodoRepository.cs, IClock.cs
│  │  └─ Todos/CreateTodo.cs, CompleteTodo.cs, ListTodos.cs, TodoDto.cs
│  ├─ TodoApp.Infrastructure/    ← adaptadores
│  │  ├─ Persistence/InMemoryTodoRepository.cs
│  │  └─ Time/SystemClock.cs
│  └─ TodoApp.Api/               ← HTTP + composition root
│     ├─ Program.cs
│     └─ Todos/TodoEndpoints.cs, DomainExceptionHandler.cs
└─ tests/TodoApp.Tests/          ← Domain, UseCases, Architecture, Api

Orden recomendado para construir: Domain → Application → Infrastructure → Api, cada paso con su test. El proyecto completo está en sample/ y la guía paso a paso en docs/GUIA-CLEAN-ARCHITECTURE.md.

Todo esto para un CRUD sin reglasSobre-ingenieríaÚsala cuando el negocio lo justifique

Protege la regla con un test

[Fact]
public void Application_DependsOnlyOnDomain()
{
    var refs = Assembly.Load("TodoApp.Application").GetReferencedAssemblies()
        .Select(a => a.Name!).Where(n => n.StartsWith("TodoApp.")).ToList();
    Assert.Equal(["TodoApp.Domain"], refs);
}

Si alguien añade una referencia prohibida, el test falla. La arquitectura deja de ser una intención y pasa a ser verificable.
