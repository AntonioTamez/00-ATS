Arquitectura Hexagonal
para novatos

También llamada Puertos y Adaptadores. Tu aplicación vive en el centro y habla con el mundo (web, consola, base de datos, email) solo a través de puertos que ella misma define. Aquí aprenderás qué es, qué va en cada parte y cómo replicarla.

1. ¿Qué problema resuelve?

El problema (Cockburn, 2005)

La lógica de negocio se mezcla con la UI (no puedes probarla sin pantalla ni usarla desde un batch) y con la base de datos (si cambia o no está disponible, todo se frena). Es el mismo error de diseño: lógica enredada con interacciones externas.

La solución

Separar dentro y fuera. Dentro: dominio y casos de uso. Fuera: todo lo demás. Se conectan por puertos (interfaces) y adaptadores (traductores a una tecnología). Así la app puede ser manejada igual por un usuario, un test o un script.

Vocabulario en 4 líneas

  • Puerto: una “conversación con propósito”; una interfaz definida por el núcleo.
  • Adaptador: traduce entre un puerto y una tecnología (HTTP, SQL, archivo, consola).
  • Primario / driving: quien maneja la app (usuario, test). Entra por un puerto de entrada.
  • Secundario / driven: lo que la app maneja (BD, email). Sale por un puerto de salida.

2. El hexágono (haz clic en cada pieza)

Adaptadores primarios
(conducen la app)

IAddBook · ILendBook · IReturnBook · IListBooks CORE (hexágono) Dominio: Book, Loan
Servicios: reglas + orquestación IBookRepository · IClock · IOverdueNotifier

Adaptadores secundarios
(la app los conduce)

Puertos de entrada a la izquierda · puertos de salida a la derecha · todas las dependencias apuntan al núcleo

Regla de dependencia (en código)

  • El núcleo no referencia ningún adaptador (ni ASP.NET, ni JSON, ni consola).
  • Los adaptadores referencian al núcleo, nunca al revés.
  • Los adaptadores no se conocen entre sí.
  • Los puertos los define el núcleo, aunque los implemente el exterior.
// Core define QUÉ necesita (puerto de salida)
public interface IBookRepository { Task<Book?> GetByIdAsync(Guid id, CancellationToken ct); ... }

// Adapters.Outbound decide CÓMO (dos adaptadores, mismo puerto)
public sealed class InMemoryBookRepository : IBookRepository { ... }
public sealed class JsonFileBookRepository  : IBookRepository { ... }

// El composition root de cada puerta elige cuál enchufar
services.AddLibraryCore().AddOutboundAdapters(jsonFilePath);

3. Recorrido de una petición

Mismo caso de uso, dos puertas distintas. Elige la puerta y avanza por los pasos.

4. Estructura de la solución

Library/
├─ src/
│  ├─ Library.Core/                  ← el hexágono (no referencia a nadie)
│  │  ├─ Domain/                     Book, Loan, DomainException
│  │  ├─ Ports/Inbound/              IAddBook, ILendBook, IReturnBook, IListBooks
│  │  ├─ Ports/Outbound/             IBookRepository, IClock, IOverdueNotifier
│  │  └─ Services/                   implementan los puertos de entrada
│  ├─ Library.Adapters.Outbound/     ← secundarios: InMemory, JsonFile, Clock, Notifier
│  ├─ Library.Adapters.Rest/         ← primario HTTP + composition root
│  └─ Library.Adapters.Cli/          ← primario consola + composition root
└─ tests/Library.Tests/              dominio · servicios · contrato · arquitectura · adaptadores

Tests: la clave hexagonal

  • Servicios: se prueban con fakes de los puertos de salida (reloj fijo, notificador espía).
  • Contrato: la misma suite corre contra cada adaptador de IBookRepository. Si un adaptador nuevo la pasa, el núcleo puede usarlo sin enterarse.
  • Arquitectura: un test falla si el núcleo referencia un adaptador.
public static TheoryData<string> Adapters => new() { "memory", "json" };

[Theory, MemberData(nameof(Adapters))]
public async Task Update_PersistsLoan(string kind) { /* mismo test, distinto adaptador */ }

5. Hexagonal vs Clean Architecture

No son rivales: Martin cita Hexagonal como uno de los antecesores que combina en Clean. Cambia el énfasis.

HexagonalClean
Dice…cómo se conecta la app con el exteriorcómo se organiza la app por dentro
Idea claveDentro/fuera, puertos y adaptadoresRegla de Dependencia hacia el centro
Estructura internaNo la prescribeEntities → Use Cases → Adapters → Frameworks
FocoSimetría de actores externosCapas concéntricas

¿Cuál priorizo? Marca lo que te pasa

Cuándo combinarlas (lo más común)

Clean dentro del hexágono (entidades, casos de uso, DTOs) + rigor hexagonal en la frontera (puertos de entrada y salida, adaptadores primarios y secundarios, tests de contrato).
