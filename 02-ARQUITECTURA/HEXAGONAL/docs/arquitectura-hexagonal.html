How to read these diagrams

Arrows point from the code that depends on something to the thing it depends on. Meaning is carried by line style and arrowhead shape, not by colour alone. Each box shows Type and, in smaller text, its namespace or project.

Solid line, filled head: calls / uses.

Dashed line, hollow triangle: implements an interface.

Dotted line, open head: DI registration / composition. In the sequence diagram a dashed line with open head is a return value.

Fill and label identify the layer. Dashed-outline boxes are test projects.

On narrow screens the diagrams scroll horizontally inside their frame; the page itself does not.

1. Hexagon overview

The core (Users.Domain and Users.Application) owns both ports. UsersController (driving adapter) calls IListUsersQuery; InMemoryUserRepository (driven adapter) implements IUserRepository. All source dependencies point toward the core.

The line from InMemoryUserRepository to the domain is the one the code really has: InMemoryUserRepository seeds through User.Register and UserRecord.ToDomain() calls User.Rehydrate.

2. Project reference graph

Taken from the <ProjectReference> elements of each .csproj. Users.Domain has none. Users.Api has no direct reference to Users.Domain (it reaches it transitively through Users.Application).

3. Sequence: GET /api/users?page=&pageSize=

Route api/users, action UsersController.List with defaults page = 1 and pageSize = ListUsersRequest.DefaultPageSize (20). Exceptions are not caught in the controller or handler; they escape the action and are translated by GlobalExceptionHandler via app.UseExceptionHandler().

Source of each throw: RequestValidationException is thrown only by ListUsersRequest.Create. In this endpoint a DomainException can only come from the Create factories invoked in UserRecord.ToDomain() (the in-memory data is seeded through valid User.Register calls, so it is not expected in practice). The action declares ProducesResponseType for 200 and 400 only; 422 and 500 come from the exception handler.

7. Code vs. patron-hexagonal.md

Where the spec and the code differ, this document follows the code.

  • Error statuses. The spec lists 200 and 400 for the endpoint. The code also maps DomainException to 422 and any other exception to 500 in GlobalExceptionHandler ([ProducesResponseType] on the action still declares only 200 and 400).
  • Api and Domain. The spec says Api depends on Application + Infrastructure only. Users.Api.csproj matches, but GlobalExceptionHandler imports Users.Domain.Common (to catch DomainException), reached transitively through Users.Application. Architecture tests only forbid this for controllers and Users.Api.Contracts.
  • Controller rule. The spec says controllers depend only on Ports.In. The test (Controllers_DependOnlyOnDrivingPorts) asserts only a forbidden list (Infrastructure, Ports.Out, ListUsersHandler, Domain). The controller does use ListUsersRequest, PagedResult and UserSummary from Users.Application.ListUsers.
  • Rehydration. The spec describes User.Rehydrate as working on trusted data. In the code, UserRecord.ToDomain() first re-runs UserId.Create, FullName.Create and Email.Create, so invalid stored data would raise DomainException; Rehydrate itself applies no transition rules.
  • Extra registration. AddInfrastructure() also registers TimeProvider.System with TryAddSingleton, which the spec's wiring summary does not mention.
  • Architecture test scope. The spec's "Application doesn't reference Infrastructure/Api" is implemented as a type-dependency check (test 3). The only assembly-reference check is the one for Domain (test 2).
