DDD táctico
para novatos

Domain-Driven Design no es una arquitectura de capas: es una forma de modelar el negocio en código para que las reglas vivan en un solo lugar, con los nombres del negocio y protegidas de modificaciones inválidas.

1. ¿Qué es y qué problema resuelve?

El problema

Evans: cuando el código de dominio está mezclado con UI y base de datos, “se vuelve extremadamente difícil de ver y de razonar”. Cambiar una regla obliga a rastrear pantallas y scripts. Y si las reglas viven en clases de servicio con entidades que solo tienen getters y setters, tienes un modelo anémico (Microsoft).

La idea

Las reglas viven dentro del modelo: entidades que protegen su estado, objetos de valor siempre válidos y agregados que garantizan consistencia. El código usa el lenguaje ubicuo del negocio: reservation.Cancel(), no SetStatus(4).

Dos mitades

EstratégicoTáctico (este portal)
¿Cómo divido el problema y hablo con el negocio? Lenguaje ubicuo, bounded contexts.¿Cómo expreso el modelo dentro de un contexto? Entidades, value objects, agregados, eventos, servicios, repositorios.

Las arquitecturas (Clean, Hexagonal…) dicen dónde van las dependencias; DDD táctico dice cómo es el modelo del centro. Se combinan.

2. Los bloques tácticos (haz clic)

¿Dónde va esta regla?

  1. ¿Afecta a un solo objeto? → dentro de ese value object o entidad (Money no admite negativos).
  2. ¿Protege una invariante del agregado? → en la raíz (Reservation.AddCharge).
  3. ¿Involucra varios agregados? → servicio de dominio (BookingService).
  4. ¿Es orquestar (cargar, guardar, notificar)? → servicio de aplicación.

Las reglas de diseño

  1. Agregados pequeños: solo lo que debe ser consistente en una transacción. Room no contiene sus reservas.
  2. Referencia por identidad: la reserva guarda RoomId, no un Room.
  3. Dentro de la frontera, consistencia inmediata; entre agregados, consistencia eventual (Evans: “Across boundaries, handle updates asynchronously”).
  4. Una transacción modifica un agregado; el resto reacciona a eventos de dominio.
  5. Solo se accede por la raíz: constructor privado, setters privados, cambios por métodos.

6. DDD frente a las arquitecturas

DDD no compite con Clean, Hexagonal, Onion o Vertical Slice: ellas organizan dependencias; DDD modela el dominio que va en el centro.

ArquitecturaDónde viven los bloques DDD
CleanEntities = agregados, entidades y VOs · Use Cases = servicios de aplicación
OnionAnillo 1 = entidades y VOs · Anillo 2 = servicios de dominio + interfaces de repositorio · Anillo 3 = servicios de aplicación
HexagonalEl hexágono es el dominio; los repositorios son puertos de salida
Vertical SliceAgregado compartido en Common · cada handler = servicio de aplicación

Las reglas, como tests

El proyecto de referencia verifica el diseño con reflection: entidades sin constructores ni setters públicos, agregados que se referencian por identidad, value objects inmutables, un repositorio por raíz (el compilador lo exige con where TRoot : AggregateRoot<TId>). Y los binarios compilados se inspeccionaron con REA (constructores y setters private/internal; el dominio sin referencias a otros proyectos).

Límite honesto: concurrencia

BookingService comprueba la disponibilidad y luego se guarda: no es atómico. Dos reservas simultáneas del mismo hueco podrían pasar. Con una base real se respalda con una restricción o control de concurrencia optimista: es el precio de la consistencia eventual entre agregados.
